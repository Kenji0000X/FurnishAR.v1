The diagrams are pages of `docs/FURNISHAR-DFD-V2.drawio` (open it at app.diagrams.net). They are generated by `scripts/build-dfd-drawio.py` from the processes in `docs/FURNISHAR-DFD-V2.md`. Every process named below maps to real code, which is cited next to it.

## How to read the diagrams

The diagrams use **Gane–Sarson** notation.

| Symbol | Meaning |
|---|---|
| **Blue box** | External entity: a person or outside system that sends data to FurnishAR or receives data from it (Buyer, Store Owner, Platform Admin, PayPal, Email Service). |
| **Rounded purple box** | Process: something FurnishAR does to data. The number says where it sits: 10.0 is a Level 1 process, 10.4 is part of 10.0, 10.4.3 is part of 10.4. |
| **Open-ended yellow box** | Data store: data at rest, for example a database table. D1–D5 at Level 1; D5.1, D5.2… when a store is split into its tables at a lower level. |
| **Dashed grey box** | A process from another diagram, shown only as a source or destination (for example 9.0 on a Level 2 page). |
| **Arrow** | A data flow, labelled with the data that moves. The arrow points the way the data goes. |
| **Two-headed arrow** | A request and its reply between a person and a process, drawn as one line to keep the page readable. |
| **"(copy)"** | The same data store drawn a second time so lines do not cross the whole page. It is not a second store. |

Three rules hold on every page:

- **Data never moves between two stores, or between a person and a store, without a process in between.** A buyer never "reads the database"; process 10.8 reads it for them.
- **Every Level 2 page is balanced with its parent.** The flows entering and leaving the page match the flows entering and leaving that process on Level 1 (see the balancing tables below).
- **Authentication and authorization are separate processes.** Knowing *who* someone is (1.0, 5.2) never, by itself, lets them open a file (5.3).

## Level 0 — Context diagram

The whole of FurnishAR is one process, **0 FurnishAR System**. Around it are the six things it talks to.

| External entity | Sends to FurnishAR | Receives from FurnishAR |
|---|---|---|
| Buyer / Guest | browsing, sign-in, planner and 3D requests, orders | catalogue, results, alerts, 3D access decisions |
| Store Owner | store application, inventory, 3D model uploads, quotes | application status, incoming orders, fees owed |
| Platform Admin | approve / reject decisions, fee settlements | applications, stores, models, audit log, usage, fee overview |
| Supabase (Auth / Postgres / Storage) | sessions, rows, authorization answers, signed URLs | sign-in requests, database queries (run as the user), signing requests |
| PayPal | approval and capture results | create-order and capture requests (payee = the shop) |
| Email Service (Gmail / Resend) | — | confirmation requests, receipts and order emails |

Two flows happen outside the system and are drawn for completeness: the **buyer pays the shop directly on PayPal**, and the **email service delivers** confirmation links, receipts, quotes and "balance due" notices to buyers, and "new order / deposit paid" notices to shops.

## Level 1 — System DFD

Level 1 opens the system into ten processes and five data stores. Supabase is no longer an external entity here: its Auth, Postgres and Storage are the data stores D1–D5.

### Processes

| # | Process | What it does | Where in the code |
|---|---|---|---|
| 1.0 | Authentication & Session | sign up, log in, role, refresh, log out | `/api/sb/auth/*`, `lib/supabase-proxy.js`, `my_role()` |
| 2.0 | Browse Collection | the public catalogue | `/collection`, `lib/catalog.mjs` |
| 3.0 | Product Details | one piece: size, price, store | `/furniture/[slug]` |
| 4.0 | Planner / Device Check | AR placement, room measurement, device support | `/plan`, `app/plan/ar-engine.js`, `/diagnose` |
| 5.0 | 3D Access & Authorization | hands out a protected 3D model only to an allowed account | `GET /api/sb/model/…`, `grantModelAccess()` |
| 6.0 | Profile / Account | a buyer's own name and town | `/account` |
| 7.0 | Store Portal | inventory, uploads, store application | `/portal` |
| 8.0 | Admin Console | review applications, see stores, models, usage, fees | `/admin/*` |
| 9.0 | Notifications / Alerts | turns every event into one clear message | `lib/alerts/*`, `AlertContainer` |
| 10.0 | Orders & Payments | buying, custom builds, PayPal, delivery, receipts | `/api/sb/orders/*`, `lib/orders.js` |

### Data stores

| Store | Holds | Tables |
|---|---|---|
| D1 Accounts & Roles | who each person is and what role they have | `auth.users` and sessions (GoTrue), `buyers`, `store_members`, `platform_admins` |
| D2 Catalogue / Products | shops and their furniture | `stores`, `products`, `product_assets`, view `catalog` |
| D3 Private 3D Assets | the model files | Storage bucket `furniture-models` (private) |
| D4 Applications / Audit / Usage | store applications, every admin decision, storage use | `store_applications`, `admin_audit`, `storage_usage()` |
| D5 Orders / Payments / Fees | orders, payments, the 10% fee, payout settings | `orders`, `payments`, `store_payout`, `fee_settlements` |

### Main flows

- **Buyer ↔ 1.0, 2.0, 3.0, 4.0, 6.0 and 10.0.** Every buyer dialog.
- **4.0 → 1.0 "session check" and 4.0 ↔ 5.0 "model request / signed URL".** The planner never touches D3 itself. Process 10.0 makes the same session check; that flow is drawn on its Level 2 page.
- **5.0 ↔ D1, D2, D3.** The only process that reads the private model bucket for a buyer.
- **10.0 ↔ D2, D5, PayPal, Email.** Stock holds, orders, verified payments and emails.
- **7.0 → D2, D3, D4.** Product changes, signed uploads, applications.
- **8.0 → D3, D4, D5.** Review, audit, fee settlements.
- **Every process → 9.0 "events", and 9.0 → Buyer, Owner, Admin "alerts".** Drawn as one shared line so the page stays readable.

### Balancing with Level 0

Every Level 0 flow appears on Level 1. The flows to and from Supabase become flows to and from D1–D5, because Level 1 shows what those services store.

### Which processes go further

Only the three processes with real internal steps and security decisions are opened at Level 2:

- **1.0:** sessions and roles;
- **5.0:** the protected 3D boundary;
- **10.0:** money.

The others stay as they are, because each does one simple thing. 2.0, 3.0 and 6.0 are single reads or writes. 9.0 is a message catalogue. 7.0 and 8.0 are add / edit / list screens over their stores. 4.0's work is geometry on the phone and involves no stored data.

## Level 2 — Process 1.0 Authentication & Session

| # | Process | What it does | Code |
|---|---|---|---|
| 1.1 | Register Account | creates the account; a database trigger writes the buyer row; the email service sends the confirmation link | `POST /api/sb/auth/signup`, trigger `create_buyer_from_signup` |
| 1.2 | Log In | exchanges email and password for an access token and a refresh token | `POST /api/sb/auth/login` (GoTrue password grant) |
| 1.3 | Resolve Role | asks the database who this token belongs to: guest, buyer, owner, pending or admin | `my_role()` |
| 1.4 | Renew Session | trades the refresh token for new tokens; a refused renewal means "session expired" | `POST /api/sb/auth/refresh` |
| 1.5 | Log Out | revokes the session on the server, not just in the browser | `POST /api/sb/auth/logout` |

**Data stores:**
- **D1.1 Auth Users & Sessions:** GoTrue's users and sessions.
- **D1.2 Roles:** `buyers`, `store_members`, `platform_admins`.

**Key point:** the role comes from D1.2 through 1.3, never from which button the person pressed. That is why a store owner who clicks "I'm shopping" still lands in their portal.

**Balancing.**

| Flow on Level 1 | On this page |
|---|---|
| Buyer ↔ 1.0 "credentials / session, role" | User ↔ 1.1, 1.2, 1.4, 1.5; 1.3 → User |
| 1.0 ↔ D1 | 1.1, 1.2, 1.4, 1.5 ↔ D1.1; 1.1, 1.3 ↔ D1.2 |
| 1.0 → Email "confirmation request" | 1.1 → Email |
| 4.0 → 1.0 "session check" | 4.0 / 10.0 → 1.3 |
| 1.0 → 9.0 "events" | → 9.0 "auth events" |

## Level 2 — Process 5.0 3D Access & Authorization

| # | Process | What it does | Code |
|---|---|---|---|
| 5.1 | Validate Model Request | the path must be `<store id>/<product id>/<file>` and a token must be present; otherwise 400 or 401 | `grantModelAccess()` |
| 5.2 | Verify Session | asks GoTrue whether the session still exists, so a signed-out token is refused at once; 401 "session expired" | `verifySession()` |
| 5.3 | Authorize & Sign Object | asks Storage to sign the file **as the user**, so the database policy decides (Level 3 below) | Storage sign + `can_view_model()` |
| 5.4 | Deliver Signed URL | returns `{url, expiresIn: 300}`: a link that works for 5 minutes | `MODEL_URL_SECONDS = 300` |

**Data stores:** D1.1 Sessions, D1.2 Roles, D2 Products · Stores · Assets, D3 Private 3D Assets.

**Key points:**
- The planner (4.0) downloads the model file **from D3 through the signed link**. It never gets a permanent address for the file.
- Every refusal goes to 9.0 as a human-readable alert: sign in, session expired, "You don't have permission to view this 3D model", or try again.

**Balancing.**

| Flow on Level 1 | On this page |
|---|---|
| 4.0 → 5.0 "model request + token" | 4.0 → 5.1 |
| 5.0 → 4.0 "signed URL / refusal" | 5.4 → 4.0, plus refusals through 9.0 |
| D1 → 5.0 | D1.1 → 5.2, D1.2 → 5.3 |
| D2 → 5.0 | D2 → 5.3 |
| 5.0 ↔ D3 | 5.3 ↔ D3 |
| 5.0 → 9.0 | 5.1, 5.2, 5.3 → 9.0 |

## Level 2 — Process 10.0 Orders & Payments

| # | Process | What it does | Code |
|---|---|---|---|
| 10.1 | Place / Cancel Order | a stocked purchase (price from D2, stock held 30 minutes) or a custom-build request; cancelling gives the stock back | `create_stock_order`, `create_custom_request`, `cancel_order` |
| 10.2 | Quote / Decline Request | the shop quotes a price and lead time, or declines with a reason | `quote_custom_order`, `decline_custom_order` |
| 10.3 | Start Payment | works out what is due now (full, 50% deposit or balance) and creates a PayPal order paid to the shop | `begin_payment`, PayPal `createOrder` |
| 10.4 | Capture & Record Payment | confirms the payment with PayPal and records it (Level 3 below) | `capture()`, `record_capture` |
| 10.5 | Fulfil & Deliver | ready → out for delivery / ready for pickup → delivered | `mark_order_ready`, `update_delivery_status`, `mark_order_fulfilled` |
| 10.6 | Notify Parties | emails the buyer and the shop about each step | `order_contacts`, `lib/notify.js` |
| 10.7 | Manage Store Billing | store type, PayPal email, delivery and pickup days, fees owed | `save_store_billing`, `store_fee_summary` |
| 10.8 | View Orders & Receipts | the buyer's orders and receipts, and the shop's incoming orders, read under row-level security | `/api/sb/rest/orders`, `/account/receipt/[id]` |

**Data stores:**
- **D2 Products:** price and stock.
- **D5.1 Orders:** status, totals, delivery details, estimated arrival.
- **D5.2 Payments & Fees:** each captured payment and its 10% fee share.
- **D5.3 Store Payout:** the shop's PayPal email and delivery days.

**Key points:**
- **Amounts always come from the database**, never from the browser: 10.3 reads the amount due from D5.1.
- **The payee is always the shop:** 10.3 reads the shop's PayPal email from D5.3.
- **Emails never block an order.** 10.6 runs after the order is updated; if the email fails, the order still stands and the failure is logged.

**Balancing.**

| Flow on Level 1 | On this page |
|---|---|
| Buyer ↔ 10.0 | Buyer ↔ 10.1, 10.3, 10.4; 10.8 → Buyer |
| Owner ↔ 10.0 | Owner → 10.2, 10.5; Owner ↔ 10.7; 10.8 → Owner |
| 10.0 ↔ D2 | 10.1 ↔ D2 |
| 10.0 ↔ D5 | 10.1–10.8 ↔ D5.1, D5.2, D5.3 |
| 10.0 ↔ PayPal | 10.3 ↔ PayPal, 10.4 ↔ PayPal |
| 10.0 → Email | 10.6 → Email |
| 10.0 → 1.0 "session check" (Level 1 draws it for 4.0 only) | 10.1 → 1.0 |

## Level 3 — Process 5.3 Authorize & Sign Object

This is the heart of the protected 3D rule. Steps 5.3.2 to 5.3.4 are the three conditions of the storage policy `can_view_model(path)` (migration 0007). The policy runs **inside the database, as the user**, so no browser or server code can skip it.

| # | Process | What it checks | Store read |
|---|---|---|---|
| 5.3.1 | Request Signature as User | sends the signing request with the user's own token, not an admin key | — |
| 5.3.2 | Check Platform Admin | is this account a platform admin? Admins may see every file, to review uploads | D1.2 `platform_admins` |
| 5.3.3 | Check Store Membership | does this account belong to the store in the file's first folder? Members may see their own files, drafts included | D1.2 `store_members` |
| 5.3.4 | Check Published & Active | is the file the model of a **published** product of an **active** store? Then any signed-in account may see it | D2 `products`, `stores`, `product_assets` |
| 5.3.5 | Issue Signed URL | D3 returns a link that expires in 300 seconds | D3 |
| 5.3.6 | Classify Refusal | a refused file and a missing file both become **403 unavailable**, so a stranger cannot learn what a shop is drafting; a storage fault becomes 502 | — |

Signed in is **necessary but not sufficient**: a buyer cannot open a draft, and one shop cannot open another shop's unpublished work.

## Level 3 — Process 10.4 Capture & Record Payment

This is where money is recorded, so every step checks something.

| # | Process | What it does |
|---|---|---|
| 10.4.1 | Fetch PayPal Order | reads the PayPal order the buyer returned with: status, stage, amount, payee |
| 10.4.2 | Re-check Amount Due | runs `begin_payment` **as the buyer**: the order must be theirs, and the amount due and the shop's PayPal email come from D5.1 and D5.3. It also releases expired stock holds. |
| 10.4.3 | Match & Capture | the PayPal order must match what is owed: same stage, amount, currency and payee. Only then is the payment captured. A mismatch, a declined card or a pending capture is reported to the buyer, and nothing is recorded. |
| 10.4.4 | Verify Recorder Secret | `record_capture` accepts the call only with the server's secret, checked against the SHA-256 hash in D5.4. A buyer calling the database directly cannot fake a payment. |
| 10.4.5 | Record Payment & Advance Order | idempotent on the capture id, so a retried call never pays twice. It checks the payee against D5.3 again, stores the payment and its 10% fee share (D5.2), moves the order to paid or deposit paid (D5.1), and restocks an expired hold if needed (D2). The estimated arrival date is stamped by the database at this point. |
| 10.4.6 | Report Outcome | tells the buyer the result, and passes "paid", "deposit paid" or "unapplied" to 10.6, which emails both parties |

**Data stores:** D5.1 Orders, D5.2 Payments & Fees, D5.3 Store Payout, D5.4 Recorder Secret Hash (the `billing_private` schema, which no client can read), D2 Products.

## Added with migration 0015 (2026-09-26)

**Level 2 — 10.14–10.17 Maya Checkout, Webhook & Payouts.**
- 10.14 answers which payment methods a shop takes, from D5.4 (its Maya row in this server's environment).
- 10.15 creates a Maya Checkout with the public key and records the attempt in D5.2: FurnishAR's reference, the payee and the fee mode.
- 10.16 settles a Maya payment. The buyer's return and Maya's unsigned webhook bring only a reference. 10.16 reads the attempt from D5.2, re-reads the payment from Maya with the secret key, claims each (payment, status) once in D5.5, records the payment once in D5.2, and emails.
- 10.17 is the admin's Maya setup per store (D5.4) and the payouts FurnishAR makes to stores (D5.6 `store_remittances`), which 7.0 shows the store.

Balances with Level 1:
- Payment Providers (PayPal / Maya) ↔ 10.0;
- 8.0 → D5 "Maya setup, payouts";
- 10.0 → Email.

On Level 0, Maya is its own external entity, because its money goes to FurnishAR's own merchant account rather than to the shop.
